- **项目**: 智能校园停车场管理系统 (parking-system)

- **被测系统**: `parking-server` (Spring Boot 3.3.0 / Java 21 / MyBatis-Plus / MySQL 8.0 / Redis)
- **环境**: 本机单机部署 (MySQL 8.0.40, Redis, HikariCP 连接池 max=20, Redis Lettuce max-active=8)

## 5. 并发正确性验证结果

### ✅ V1 重复出场幂等 (30 并发)
- 成功 1 / 失败 29 (错误均为 `Vehicle has already exited`)
- 余额 200 → 195, 仅扣款一次 ¥5.00, 数据库仅 1 条对应扣费记录
- **结论: 无重复扣费, 幂等保护有效**

### ✅ V2 余额不足保护
- 余额 ¥5.00 → 出场扣 ¥5.00 → 余额 0.00
- 再次出场被拦截: `Insufficient balance. Please recharge. Required: 5.00 yuan`
- **结论: 余额不足被拦截, 余额永不为负**

### ⚠️ V3 并发充值 (10 并发充值 ¥100)
- 成功 6 / 失败 4, 错误均为 `服务器内部错误`
- 根因: `order_no` 由 `"RECH" + System.currentTimeMillis()` 生成, **同毫秒并发生成相同订单号, 触发 `t_recharge_record.uk_order_no` 唯一索引冲突**
- 实际入库 6 笔, 余额 +600 (非预期 +1000)
- **结论: 存在并发缺陷, 详见 §6-1**

### ✅ V3 并发扣费 (5 用户同时出场)
- 5/5 成功, 所有用户余额非负, 均生成扣费流水
- **结论: 乐观锁扣款 (`balance >= amount` 条件更新) 并发正确**

### ✅ 压测后数据一致性
- 车位状态: 49 空闲 + 1 维护中 (与压测前一致, 无残留占用/预约)
- 在场车辆: 0 (全部正常释放)
- 扣费流水: 161 笔 / ¥746.10, 充值流水 18 笔 / ¥1800.00, 与各用户余额变动吻合

## 6. 发现的问题与缺陷

### 6-1 🔴 充值订单号并发冲突 (严重)
- **位置**: `UserServiceImpl.recharge()` (第 67 行)
- **问题**: `record.setOrderNo("RECH" + System.currentTimeMillis())` — 同一毫秒内的并发充值请求生成相同 `order_no`, 撞 `uk_order_no` 唯一索引, 请求抛 `DuplicateKeyException` 返回 500, 且**余额未增加** (用户充值失败)
- **实测**: 10 并发充值失败 4 笔
- **建议**: 使用雪花 ID / UUID / 序列号生成订单号, 或加随机后缀

### 6-2 🟠 微信登录空手机号唯一索引冲突 (严重, 线上注册即触发)
- **位置**: `AuthServiceImpl.wechatLogin()` + `t_user.uk_phone`
- **问题**: 微信登录创建的用户的 `phone` 为空字符串 `''`, 而 `t_user` 表对 `phone` 建有 **UNIQUE 索引**。第一个微信用户注册成功后, **任何后续微信新用户注册都会报 `Duplicate entry '' for key 't_user.uk_phone'`**, 即线上仅能注册 1 个微信用户
- **实测**: 压测准备阶段首次触发, 后续所有新微信用户注册全部失败 (该缺陷同时导致 `prepare.js` 无法批量建号, 测试改用 SQL 直插 + 本地签发 JWT 绕过)
- **建议**: 空串不参与唯一索引 (MySQL 8 无部分索引, 可将 phone 改为 NULL 存 NULL, 或去掉 uk_phone 索引改由业务层校验)

### 6-3 🟡 车位概览/工作台接口性能瓶颈
- `GET /api/spot/overview` 与 `GET /api/admin/dashboard` 无缓存、聚合查询多表
- 并发 50 时 p50 已达 616ms / 2106ms; 并发 200 时 overview p50 恶化至 2770ms
- 该接口为小程序首页高频轮询接口, 建议加 Redis 缓存 (短 TTL) 或拆分统计查询

### 6-4 🟡 部分雪花 ID 前端精度丢失
- `PaymentRecord.vehicleRecordId` / `userId` 等字段**未加** `@JsonSerialize(using = ToStringSerializer.class)` (仅 `id` 主键加了)
- 雪花 ID (19 位) 超过 JS `Number.MAX_SAFE_INTEGER` (2^53-1), 序列化为数字时前端精度丢失 (实测 `2090616698834522112` 返回为 `2090616698834522000`)
- **建议**: 所有 Long 主键/外键统一序列化为字符串

### 6-5 🟡 压测环境暴露: 登录验证码 + Redis 依赖
- 账号密码登录/注册强依赖图形验证码 (Redis 存储), 并发压测时验证码接口 (`/api/auth/captcha`) 每次生成 Base64 图片, 属额外开销
- 生产环境建议验证码接口限流, 防止被刷

## 7. 性能评估结论

| 指标 | 评估 |
|---|---|
| **并发正确性** | ✅ 优秀: CAS 车位抢占 (入场/预约 30 并发仅 1 成功)、乐观锁扣款、出场幂等、余额不为负均验证通过 |
| **登录接口** | ✅ 良好: QPS 470~481, p99 < 700ms (200 并发) |
| **普通读写接口** | ✅ 良好: 车位/用户/记录类接口 QPS 110~150, p95 < 600ms |
| **概览/工作台** | ⚠️ 瓶颈: QPS < 80, 高并发下 p50 > 2.7s, 建议加缓存 |
| **并发写入** | 🔴 充值接口存在订单号冲突缺陷 (6-1); 入场/出场/预约写入逻辑本身并发安全 |

**总体**: 系统核心并发安全设计 (CAS + 乐观锁) 正确可靠, 常规接口在 50~200 并发下稳定无错误; 主要风险集中在**充值订单号生成**与**微信注册唯一索引**两个业务缺陷, 以及**概览聚合接口**的性能瓶颈。

## 8. 修复记录 (2026-08-21 已修复并发充值 + 出场竞态)

### 8-1 ✅ 充值订单号并发冲突 (已修复)
- **改动**: `UserServiceImpl.recharge()` — `orderNo` 由 `"RECH" + System.currentTimeMillis()` 改为 `"RECH" + 雪花ID (sf.nextId())`
- **验证**: 10 并发 / 20 并发 / 50 并发充值 **100% 成功**, 余额精确一致, 订单号全部唯一
  - 50 并发: 50/50 成功, 余额 +5000.00 精确一致, 订单号 50 个全部唯一

### 8-2 ✅ 出场结算并发竞态 (修复中连带发现并修复, 资金安全)
- **问题**: `VehicleServiceImpl.exit()` 与 `AdminServiceImpl.forceExit()` 均为"先查后改" (`record.getStatus() != 0` 检查 + 随后 `updateById`), 并发下多个请求可同时通过检查 → **同一停车记录被重复扣款**
- **实测**: 修复前 30 并发重复出场 **20 次扣款成功** (扣款 ¥100), 修复后 **仅 1 次成功扣款** (扣款 ¥5)
- **改动**: 参照 `enter()` 的 CAS 模式, 出场/强制出场先用原子更新抢占状态 (`status 0/2 -> 1`, `WHERE id=? AND status=?`), 更新行数为 0 即拒绝, 后续扣款失败由 `@Transactional` 回滚
- **验证**: V1 幂等测试 30 并发 → 1 成功 29 失败, 仅扣款一次 ✓

### 8-3 ✅ 预约编号并发冲突 (连带修复)
- **改动**: `ReservationServiceImpl.createReservation()` — `reservationNo` 由 `"RES" + System.currentTimeMillis()` 改为 `"RES" + 雪花ID`, 消除不同车位同毫秒并发预约撞 `uk_reservation_no` 的隐患

### 8-4 回归验证
- 完整压测套件 (S1~S7) 并发 50 全部通过, 无退化
- V1/V2/V3 专项并发正确性验证全部通过

- 🟡 概览/工作台接口无缓存 (6-3): 建议加 Redis 缓存
