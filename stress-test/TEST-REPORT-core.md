## 二、发现的 Bug 清单

### 🔴 Bug-1(严重): 微信登录注册新用户必然 500 — uk_phone 空串冲突
- **现象**: `POST /api/auth/wechat-login`(新 deviceId)返回 `code:500 服务器内部错误`;任何新用户都无法通过微信登录创建账号。
- **根因**: `AuthServiceImpl.wechatLogin()` 创建用户时**不设置 phone**,MyBatis-Plus 插入语句省略 `phone` 列 → 落库为列默认值 `''`;而 `t_user.uk_phone` 为唯一索引。数据库已存在 1 个 `phone=''` 用户(`wx_smoke-*`)时,新插入直接报 `Duplicate entry '' for key 't_user.uk_phone'`。即便空 phone 行不存在,**第二个**微信用户也会撞同一唯一索引(空串不允许重复,MySQL 唯一索引只允许多个 NULL)。
- **复现**: `node e2e-core.js` 用例 T15(连续两轮跑均稳定复现)。
- **修复建议**(任选):
  1. 创建微信用户时显式 `user.setPhone(null)` 并把列改为允许 NULL(默认 NULL),唯一索引对多行 NULL 不冲突(需注意 MyBatis-Plus 默认不插入 null 字段,要改列默认值或改用自定义 insert);
  2. 用 `openid` 派生一个内部唯一占位手机号(不推荐,破坏手机号语义);
  3. 表结构层面为微信用户提供独立 phone 生成(如 `wx_<id>`)或去掉 uk_phone 对 `''` 的约束(如加 `binding_status` 列做条件唯一)。
- 另外该接口未对唯一键冲突做兜底处理,属于"异常未捕获直接 500",建议捕获 DuplicateKeyException 返回明确业务提示。

### 🟠 Bug-2(中高): 未预约用户可以抢停他人"已预约"车位
- **现象**: 用户 D 预约车位后该车位状态=2;用户 E(无该车位预约)直接 `POST /vehicle/enter` **成功入场**,D 的预约形同虚设(其后 E 占位,D 到场无法凭预约入场,车位被占)。
- **根因**: `VehicleServiceImpl.enter()` 对车位状态校验 `spot.getStatus() != 0 && spot.getStatus() != 2` 才拒绝,即 status=2(他人预约)被视为"可入场";且 CAS 条件 `.in(status, 0, 2)` 同样放行。未校验"车位当前活跃预约是否属于入场用户/本次携带了预约单"。
- **佐证**: 小程序 `pages/enter/enter.js` 注释明示 "Show vacant (0) and reserved (2) spots; both are valid for entry"——前后端把"他人已预约"也当成了可入场车位,与"预约锁定车位"的产品语义冲突。
- **修复建议**: 当 `spot.status == 2` 时必须校验 `dto.reservationId` 非空且该预约属于当前用户并指向该车位;否则拒绝("该车位已被他人预约")。

### 🟠 Bug-3(中高): 同一用户并发向两个不同车位入场,两笔都成功(可同时停两辆车)
- **现象**: 用户 H 同时向 A-011、A-012 两个空闲车位发起入场,两请求均成功 → 同一用户同时存在 2 条 `status=0` 在场记录,占 2 个车位。
- **根因**: `enter()` 里的"用户是否已有在场车辆"是先 `selectCount` 再插入的 TOCTOU(检查与插入无原子性、无锁、无唯一约束),两次并发都读到 count=0。
- **复现**: e2e 用例 T56(`Promise.all` 并发双入场)。
- **修复建议**:
  1. 入场前对用户记录 `SELECT ... FOR UPDATE` 串行化(简单);
  2. 或用 Redis 分布式锁按 `userId` 加锁;
  3. 或建 `(user_id, status)` 唯一约束的辅助表/生成列,由 DB 兜底拒绝第二辆。
  (注意:同一**车位**的双入场已被 CAS 正确拦截——用例 T55 通过;只有"同一用户不同车位"存在竞态。)

## 三、次要问题/观察项(不阻塞主流程)

1. **ID 序列化不一致(低)**: `/auth/login`、`/auth/register`、`/auth/wechat-login` 返回的 `userId` 是裸 Long(JSON 数字,约 2.09e18 > 2^53),JS/小程序端解析即丢精度;而实体/管理端列表用 `ToStringSerializer` 输出字符串。小程序若回传该 userId 或与列表 id 比对会出错。建议 auth 返回与实体一致使用字符串序列化。
2. **`/admin/spot-map` 的 spot `id` 为裸数字(低)**: `AdminServiceImpl.getSpotMap()` 手动 HashMap 未加 `ToStringSerializer`,同上有精度风险;当前 React 管理端仅展示不回传,不受影响。
3. **计费起步规则不一致(低)**: `exit()`/`forceExit()` 中 `minutes<=0`(停车不足 1 分钟)强制按 1 小时收费 5 元;但停 1~59 分钟按分钟向上取整计费,例如停 61 秒仅 ¥0.10、停 59 分钟 ¥4.95——出现"停得越久单价比 1 分钟内更便宜"的倒挂边界。若以"不足 1 小时按 1 小时"为起步价,应统一 0~60 分钟皆按 1 小时(或统一按分钟)。(小程序结算页展示与后端口径需一致。)
4. **小程序入场页设计**: 允许用户进入任意 status 0/2 车位,是 Bug-2 的前端诱因,修复后端时需同步小程序文案/交互。

## 四、通过的核心链路(冒烟结论)

注册 → 登录 → 设置车牌 → 充值 → 查询空闲车位 → 预约(2h) → 入场 → 出场自动按 max(实际,预约额)扣费 → 车位释放 ✅
直接入场 → 在场拦截 → 出场 1 小时起步扣费 → 车位释放 ✅
余额不足出场被拒(不扣费、不丢在场状态)→ 充值 → 再出场成功 ✅
管理员登录 → 用户搜索/禁用(自动清理其在场车与预约)/启用 → 预约管理 → 强制离场 → 车位维护/地图 → 配置修改 ✅
过期预约 → 调度器(60s)自动标记过期并释放车位 ✅
并发: 同车位双预约/双入场/双出场均由 CAS 保证只成功一次 ✅

## 五、结论

核心链路整体可用且对"同车位并发"做了正确的 CAS 防护,预约-入场-计费-扣费-释放闭环正确;存在 **1 个严重(微信登录新用户 500)+ 2 个中高(预约车位可被抢停、同用户并发双入场)** 需优先修复。已附最小复现(见各 Bug 的"现象/复现"与 `e2e-core.js` 对应用例)。
